# 自作Android IME 設計仕様書

## 概要
Android用の自作ソフトウェアキーボード(IME)。30%キーボードのようにキー数を絞り、
レイヤー切り替えで機能を切り替える設計。

## 技術方針
- `InputMethodService` を継承した独自IMEとして実装(Kotlin想定)
- ローマ字→かな変換、および将来的な漢字変換(かな漢字変換)は、
  Mozcエンジンを組み込んだ既存OSS(例: mozkey, OyaMozc)をforkして土台にする方向を検討中。
  ゼロから変換エンジンを実装するのではなく、既存実装のレイヤー/キー配置部分を
  自分の設計に置き換えるアプローチを優先する。
- 全角/半角の切り替えは、ASCII文字とUnicode全角文字の対応表による単純変換で実装可能。
  適用範囲は「直接英数入力」および「レイヤー2(数字・記号)」の両方。全角モード中は
  レイヤー2の数字・記号キーも全角文字で入力される。ローマ字→かな変換/漢字変換は
  もともと全角の日本語として確定するため対象外(常に全角相当)。
  (2026-08-22追記: ローマ字入力モード中のレイヤー2(数字・記号)は、上記の手動トグルの
  状態に関わらず常時全角。日本語文章に混在させる数字・記号が半角のままになるのを防ぐため。
  直接英数モードのレイヤー2は従来通り手動トグル(既定は半角)に従う。)

## 物理レイアウト
- 4段構成(数字専用の段は設けない)。いわゆる30%キーボード(Planck等)に近い配列。
  - 1〜3段目: レイヤーごとに中身が入れ替わるキー配列(26キー相当)。
    3段目は左端にShift、右端にBackspaceを置き、その間に文字キーを中央寄せで並べる
    (2026-09-05改訂)。Shiftを4段目から外したのは物理QWERTYと同じ位置であることに加え、
    4段目に句読点の枠を空けるため。ローマ字入力中もShiftは表示されたままだが、これは
    レイヤー2のShift併用キー `_` `"` がローマ字入力中にも必要なため意図的。
  - **キー幅の基準は1段目**(2026-09-05追加)。1段目は文字キーのみの10キーで画面幅を等分し、
    2段目・3段目のキーはこの「1段目のキー1つ分」と同じ幅で描く(足りない分は余白になる)。
    2段目は左右に均等な余白を置いて中央寄せ、3段目はShiftを左端・Backspaceを右端に固定し、
    間の文字キーだけを中央寄せにする。レイヤー1とレイヤー2で3段目のキー数が違っても
    (7文字 対 8記号)、この固定によりShiftとBackspaceの画面上の位置は一致する。
  - 4段目: 機能キー段。**レイヤー1・レイヤー2で完全に共通**の位置・構成とする。
    レイヤー切り替え時は1〜3段目のみが入れ替わり、4段目は一切変化しない。
    構成は左から右へ
    `レイヤー切替 / 句読点 / スペース(幅広) / 句読点 / ローマ字入力切替 / エンター`。
    入力モードによって変わるのは**スペースの両隣に置く句読点の字形だけ**で、キーの数・
    位置・並び順は一切変わらない。
    - **直接英数入力モード中**: スペースの左が `,`、右が `.`
    - **ローマ字入力モード中**: スペースの左が句点 `。`、右が読点 `、`
    (2026-09-05改訂: 当初は直接英数モードの4段目左端がShiftで、句読点の代わりに
    そこを占めていた。その結果**直接英数入力でカンマとドットがまったく打てなかった**ため、
    Shiftを3段目へ移し、空いた2枠を両モードとも句読点に充てた。これにより4段目は入力モードを
    跨いでも位置が変わらなくなった。2026-08-22改訂でモード別の2パターンにした経緯も参照。)
    - スペースキーを中央付近に置き、頻度の高い切替操作(レイヤー切替・ローマ字入力切替)を
      その周辺に配置することで、親指で届きやすくする。
    - スペースキーは他キーより幅広に確保する
- Backspaceキー: **3段目の右端**に配置(2026-09-05改訂。当初はQWERTY最上段の右に11個目の
  キーとして置いていたが、1段目を文字キー10個ちょうどにしてキー幅を広げるため移動した)。
  レイヤー1・レイヤー2の両方で同じ位置になる(レイヤーを跨いでも位置が変わらない)。
  長押しで一定間隔ごとに削除を繰り返す(リピート削除)。

## レイヤー構成(トグル型切り替え)
レイヤー切り替えキーは「押すたびに固定/解除」されるトグル方式。
現在のレイヤーが一目でわかるよう、配色や切り替えキーの見た目を変える等の
視覚的フィードバックを必ず入れる。

### 視覚的フィードバックの統一ルール
- **レイヤー**: キーボード全体の背景色をレイヤーごとに変える(レイヤー1/レイヤー2で
  異なるテーマ色を割り当てる)。
- **トグル/ロック状態の共通ルール**: 「固定中のキーは塗りつぶし表示、解除中は通常表示」
  というルールを、以下すべてのトグル/ロック状態に共通で適用する。
  - レイヤー切り替えキー(レイヤー2に固定中)
  - シフトキー(素早い2回タップでロック中)
  - ローマ字入力切り替えキー(直接英数モード中)
- 上記により、キーボード内のどのトグル系キーも「今どちらの状態か」を同じ視覚言語で
  判断できるようにする。
- シフトキーのロック色のみ、他のトグル系キー(レイヤー切替・ローマ字入力切替)のロック色
  より明るさを半分程度落とした色を使い、視覚的に区別できるようにする(2026-08-22追加)。
- **モーメンタリのシフトは、ロック色よりさらに薄い色で塗る**(2026-09-06追加)。
  「固定中=塗りつぶし」ルールの例外ではなく、固定とarmedを濃淡で区別する。
  これがないと、シフトを押しても画面が何も変わらない状況(ローマ字入力中のレイヤー1は
  かなに大文字小文字がないためキーラベルも変わらない)でarmedかどうか判別できず、
  モード切替時に原因不明のまま大文字表示に変わる、といった混乱が起きる。
  なお触覚フィードバックはロックの固定/解除のときだけで、モーメンタリでは鳴らさない。
- **全角モードは塗りつぶしではなく枠線で示す**(2026-09-05改訂)。ローマ字入力切り替えキーは
  「直接英数モードON」と「全角モードON」という**互いに独立した2つの状態**を1つのキーで
  背負っており、当初は「どちらかがONなら塗りつぶす」という論理和にしていた。その結果
  全角をONにしたときの見た目が直接英数モードONと区別できず、長押しが暴発しても気づけな
  かった。塗りつぶし=入力モード、枠線=全角、と channel を分けることで、4通りの組み合わせが
  すべて読み取れるようにする。枠線の色は塗りつぶし色(青系)と重ねても見えるよう暖色にする。

### レイヤー1(基本レイヤー)
- ローマ字キー(QWERTY配列、26キー)。1段目 `qwertyuiop`(10キー)、2段目 `asdfghjkl`(9キー、
  中央寄せ)、3段目 `Shift zxcvbnm ⌫`(Shiftが左端・Backspaceが右端、文字は中央寄せ)
- Backspaceキー: 3段目の右端に配置
- スペースキー:
  - タップ: 半角スペース入力
    - ただし、かな漢字変換の候補選択中(未確定文字列がある状態)にタップした場合は
      「次候補」へ送る動作になる(下記「かな漢字変換操作」参照)
  - 長押し: Tab入力
  - 左右スワイプ: カーソルを左右に移動(Gboardのカーソル移動ジェスチャーと同様)
    - 実装方式: 上下スワイプ(行移動)と同じく、固定閾値を跨ぐたびに1文字移動する
      ドラッグ操作方式。指を離すまで連続して複数文字移動できる。
  - 上下スワイプ: カーソルを上下(行単位)に移動
    - 実装方式: 固定閾値(縦方向の移動量)を跨ぐたびに1行移動する、ドラッグ操作に近い方式。
      指を離すまで連続して複数行移動できる。左右スワイプのカーソル移動と同じロジックを
      縦方向に流用する形で実装する。閾値の具体的な数値は実装しながら調整する。
  - 候補選択中に長押し/スワイプを行った場合: 先頭候補を確定してから、通常時と同じ動作
    (Tab入力 / カーソル移動)を実行する。
- エンターキー: `EditorInfo.imeOptions` に応じて動作・ラベルを動的に切り替える
  (例: 検索欄では「検索」ラベル+検索実行、通常のテキスト欄では改行など、
  Android標準のIME Action慣習に従う)。
- シフトキー(3段目の左端。2026-08-22改訂: ロックのトリガーを長押しから素早い2回タップに変更):
  - タップ: モーメンタリ(次の1文字のみ大文字化、入力後は自動解除)
  - 素早い2回タップ(300ms以内): ロック(CapsLock的に常時大文字化。解除は再度タップ)
- ローマ字入力切り替えキー:
  - タップ: ローマ字入力 ⇄ 直接英数入力の切り替え
    - 直接英数入力モード中は、Mozcのかな漢字変換処理を完全にバイパスする。
      候補バーは表示されず、キー入力はそのまま文字として確定される
      (スペースキーの「次候補」動作も発生せず、常に通常のスペース入力になる)。
    - **切り替え時はShiftを必ず解除する(両方向、2026-09-06改訂)**。当初は
      直接英数→ローマ字の向きだけ解除していたが、逆向きでバグになっていた:
      ローマ字入力中はレイヤー1の文字キーがShiftを無視する(かなに大文字小文字がない)ため
      Shiftを押しても画面が変わらず、モーメンタリは塗りつぶし表示もされない。その状態で
      あ/Aを押すと、原因が見えないままキーボード全体が突然大文字表示になっていた。
  - 長押し: 全角 ⇄ 半角の切り替え(キーラベルは `あ/A`)
    (2026-09-05: ラッチ系のジェスチャーをShiftのロックに揃えるため一度「素早い2回タップ」に
    変更したが、同日中に長押しへ戻した。連続タップだと1回目のタップで先に入力モードが
    切り替わってしまい、それを2回目で打ち消す必要があるのに対し、長押しはタップ自体を
    抑止するので副作用がない。Shiftのロックは連続タップのまま)
- レイヤー切り替えキー(トグル): レイヤー2へ切り替え

### レイヤー2(記号・数字レイヤー)
ASCII記号32種のうち `,` `.` を除く30種すべてを打てる。多くのキーにShift併用の第2の文字を
割り当てることで、レイヤーを増やさずに収めている(2026-09-06改訂。それ以前は
`!` `$` `%` `&` `;` `=` `?` `\` `^` `|` がどのレイヤーからも入力できなかった)。

**ペアの決め方**: 両方の文字がUS配列の同じキーに載っているものは、その組み合わせをそのまま
使う(`[`/`{`、`` ` ``/`~`、`/`/`?`、`-`/`_`、`'`/`"` など)。覚え直しを不要にするため。
ただし**どちらを非Shift側に置くかはMarkdownでの使用頻度で決める**ので、次の2組はUS配列と
逆になっている。

- `>` / `<` — `>` は引用記法で常用、`<` はほぼ使わない
- `|` / `\` — `|` は表組みで常用、`\` はエスケープ程度

**Shift中はキーの表示文字が切り替わる**(2026-09-06追加)。`[` と `{` のように無関係な字形の
ペアでは、大文字小文字と違って表示から推測できないため。

- 1段目(数字10キー): `1 2 3 4 5 6 7 8 9 0`
  - Shift併用でUS配列どおり `! @ # $ % ^ & * ( )`
- 2段目(10キー、中央寄せ): `( ) [ ] * ` > | - #`
  - **Markdownで最も使う10記号を非Shift側に集めた段**。この段だけでMarkdownの基本記法
    (見出し・箇条書き・強調・コード・リンク・引用・表)がShiftなしで書ける
  - Shift併用: `[`→`{`、`]`→`}`、`` ` ``→`~`、`>`→`<`、`|`→`\`、`-`→`_`
  - `-` はローマ字入力中の非Shift側では長音符「ー」として未確定の合成に合流する
  - `-`(=「ー」)と `#` は右端に並べる。`#` が最も外側
- 3段目(Shift + 7キー + Backspace、計9キー): `Shift / : = ' ! & @ ⌫`
  - Shift併用: `/`→`?`、`:`→`;`、`=`→`+`、`'`→`"`
  - `!` と `&` はShift+1 / Shift+7 でも打てるが、画像記法 `![](…)` とURLのクエリ文字列で
    多用するため専用キーも置く(`(` `)` をShift+9 / Shift+0 と重複させているのと同じ理由)
  - `@` はBackspaceの左隣
  - レイヤー1の3段目と同じ9キー構成なので、レイヤーを切り替えても3段目のキー位置は動かない
- 4段目(機能キー段): レイヤー1と完全共通
- レイヤー切り替えキー(トグル): レイヤー1へ戻る
- Markdown記法(#, *, `, >, -, |, [ ] など)はこの配置で対応する。専用のMarkdown入力レイヤーは
  現時点では設けない(将来、記号ではなく `- [ ]` や ``` のような複数文字のスニペットを
  置く場所としてレイヤー3を検討する)

## かな漢字変換操作(Mozc統合時)
- 「変換」専用キーは設けない。ローマ字入力に応じて候補バーに変換候補を自動表示する、
  Gboard日本語などのモバイルIME標準スタイルを採用する。
- 候補バーはキーボード上部(1段目のさらに上)に常設の帯として確保する。
  候補が何もない状態(ローマ字入力開始直後など)では空白のまま何も表示しない
  (予測変換は行わない)。
- 候補は横一列に並べ、収まりきらない分は横スクロールで表示する。
  タップで即確定、スペースキーのタップで次候補へ送る(前述の通り)。
- 「次候補」(候補送り): 候補選択中(未確定文字列がある状態)にスペースキーをタップすると
  次の候補へ送る。未確定文字列がない通常時は、スペースキーのタップは半角スペース入力。
- 候補確定: 候補バーのタップで即確定(タップした候補が、フォーカス中のものと違っても
  そのタップした候補で確定される。Mozcの`SessionCommand.SUBMIT_CANDIDATE`に候補のid
  を渡すことで実現、2026-08-22実装)。何もせず次の文字入力を行った場合は先頭候補が
  自動確定される。
- 複数セグメントへの変換(長文をローマ字入力して変換した場合など、2026-08-22追記):
  Enterは全セグメントを一括確定せず、フォーカス中の先頭セグメントのみを確定し
  (Mozcの`SessionCommand.SUBMIT_CANDIDATE`)、残りは引き続き未確定の合成として表示・
  変換対象のままになる。以後もEnterのたびに先頭から1セグメントずつ確定され、
  変換対象が尽きると通常通りすべて確定済みになる。単一セグメント(候補が1個の変換)の
  場合は結果的に通常のEnter確定と同じ挙動になる。
- 句点(。)/読点(、)(2026-08-22追記): 未確定のローマ字合成がある場合、それを強制確定
  させず合成に合流させる(ローマ字キーと同じ扱い)。合成が何もない状態では、そのまま
  確定済み文字として直接入力される。
- レイヤー2の数字キー(2026-09-21追記): 句読点と同じ扱い。未確定のローマ字合成がある
  場合は強制確定させず合成に合流させるので、「だい」+「1」→「だい１」のように数字を
  混ぜたまま変換・編集を続けられる。Mozcはひらがなモードの未確定文字列で数字を全角に
  するため、見た目は従来の全角出力のまま。合成が何もない状態では従来どおり
  そのまま全角数字として直接入力される(数字を打つだけで未確定文字列とEnterが増えない
  ようにするため)。Shift併用時の `!@#…` は従来どおり半角ASCII記号として確定入力。

## 入力欄の種類による自動切り替え(2026-09-02追加)

フォーカス中の入力欄の`EditorInfo.inputType`を見て、変換パイプラインをどこまで有効に
するかを自動で決める(`EditorInfoInputModeMapper`)。3段階:

- **通常**(それ以外すべて): 従来どおりローマ字入力モードで開始し、候補バーも出す。
- **既定で直接英数**(メールアドレス / URI / 数値 / 電話番号 / 日時): 直接英数入力モードで
  開始する。ただしローマ字入力切替キーは生きており、ユーザーが日本語に切り替えるのは自由
  (URL欄に日本語を打つ場面はあるため)。
- **変換を完全に抑止**(パスワード欄: テキスト/可視/Web/数値パスワード): 直接英数入力モードで
  開始し、**候補バーは非表示**(高さごと消す)、**ローマ字入力切替キーは無効**。
  パスワードが候補バーに平文で出るのを防ぐため、その欄にフォーカスしている間は
  かな漢字変換そのものを動かさない。

## 未確定文字列とカーソル移動の同期(2026-09-02追加)

変換中にユーザーがテキストを直接タップしてカーソルを動かした場合、`onUpdateSelection`で
それを検知し、未確定文字列をその場で確定(`finishComposingText`)してMozcセッションを破棄する。
これをやらないと、エディタ側は合成範囲を離れているのにIME側が合成を保持したままになり、
次の打鍵が元の位置に差し込まれて文字が入れ替わる。

判定はエディタが合成範囲(`candidatesStart`/`candidatesEnd`)を報告している場合のみ行う。
WebViewなど合成範囲を常に-1で返す実装があり、そこで「ユーザーが移動した」と誤判定すると
1打鍵ごとに変換が壊れるため、報告がない場合は何もしない。

## 未確定・今後決めること
- 視覚的フィードバックの具体的な配色(実際のカラーコード)。ルール自体は確定済み
  (上記「視覚的フィードバックの統一ルール」参照)だが、具体的な色の値は未定。
- スペースキー上下スワイプの閾値の具体的な数値(実装しながら調整)

## 実装上の注意点
- スペースキー1つに「タップ／長押し／左右スワイプ／上下スワイプ」の4種のジェスチャーが乗り、
  かつ「かな漢字変換の候補選択中かどうか」で意味が変わる状態依存キーになるため、
  タッチイベント処理での移動距離の閾値・長押し判定タイマーによる分岐に加えて、
  IME側の変換状態(未確定文字列の有無)を参照した分岐が必要。
- レイヤー切り替え時は `Keyboard` オブジェクト(表示するキーレイアウト)を
  差し替える実装になる。Backspaceキーなど両レイヤー共通のキーは同じ位置に
  配置し、レイヤー切り替え時の位置感覚のズレを防ぐ。
- 触覚フィードバック(バイブレーション): 通常のキー入力タップでは鳴らさず、
  「トグル切り替え・Shiftロックなど状態が変化した瞬間」のみ短い振動を発生させる。
  視覚的フィードバック(塗りつぶし表示)と対になる形で、状態変化を触覚でも伝える。
